# 수동 제어 우선 개발 작업지시서

작성: 2026-11-21 · 상태: 요구사항 확정, 실물 배선 미확정 · 첫 목표: 사용자가 직접 시작하는 수동 시험 소프트웨어

## 1. 이번 요청과 완료 범위

노션의 목적·동작을 먼저 검토하고 이 지시서와 실행 프롬프트를 만든 다음 `/goal`로 구현한다. 이번 단계는 수동 제어를 준비하고 하드웨어 없는 시험을 통과시키는 것이다. 에이전트는 모터·리프트·GPIO·센서 취득을 실행하지 않는다. 설치, VS Code 열기, 프로그램 import, 페이지 접속만으로 출력이 발생하면 안 된다. 실제 출력은 현장 확인을 마친 사용자가 실물 모드 실행, 제어권 획득, ARM, 조작 입력을 직접 수행했을 때만 허용한다.

**소프트웨어 준비 완료와 실물 구동 성공은 별개다.** 첫 단계 완료 시 `SOFTWARE_READY / HARDWARE_PENDING`으로 기록한다. 배선·극성·전원·리미트를 추측하거나 확인 플래그를 에이전트가 true로 바꿔 완료 처리하지 않는다.

## 2. 전체 목적과 단계 연결

최종 목적은 단일 Raspberry Pi 5에서 물류 입고 → ID 식별 → 목적지 결정 → 위치·지도 확인 → 이동 → 집기 → 운반 → 하단/상단 적치 또는 하역 → 위치·재고 기록 → 출고 확인을 수행하는 것이다. 운용 판단과 기록은 로컬에서 이루어진다. 현재 Tailscale·VS Code·Codex는 개발 접근 경로이며 오프라인 자율 운용이 입증된 것은 아니다. [N1][N2]

## 3. 현재 환경과 코드 검토 결과

- 확인한 환경: Debian 13.7 aarch64, Pi 5. 공동 경로 `/srv/jongsul/forklift`. 각 팀원은 본인에게 발급된 개인 Linux/Codex 계정과 SSH 별칭으로 접속한다. 장치 주소와 개인 로그인 정보는 GitHub 공유 문서에 포함하지 않는다.
- 기존 파이 프로젝트의 현재 수동 진입점은 `motor_control/manual_control.py`이다. 원본을 수정하거나 실행하지 않고 새 `manual_station` 폴더에 준비한다. `releases` 아래 코드는 과거 스냅샷이다.
- 현 코드의 회전 혼합은 일부 바퀴를 선택 출력과 무관하게 100%/50%로 명령한다. 새 도구는 검증한 출력 상한을 어떤 방향에서도 넘지 않는다.
- 현 수동 도구는 시작 때 GPIO를 열고, 입력 루프와 별도 액추에이터 watchdog 연결도 불완전하다. 그대로 감싼 자동 실행 래퍼를 만들지 않는다.
- 시스템에 gpiozero 2.0.1/lgpio 0.2.2.0 파일이 있고 Python3.13 공유 환경에서 system-site-packages가 설정되어 있다. 이는 파일 확인이며 GPIO import/실물 접근 시험이 아니다. lgpio import 자체도 통지 스레드/FIFO를 만들 수 있어 mock/default에서는 import하지 않는다.
- 기존 `rebuild/state.json`의 접속 관련11/20 정보는 이번11/21 확인으로 갱신하되 `gpio_mapping_confirmed=false`, `ready_for_motor_output=false`, `lift_output_enabled=false`는 유지한다.

### 핀 출처 충돌 — 자동 선택 금지

| 채널 | 현재 Pi `forward_wheels.py`의 BCM IN1/IN2/EN | 10/27 노션의 전후 채널 BCM IN1/IN2/EN |
|---|---|---|
| front-A | 3/4/2 | 17/27/18 |
| front-B | 17/27/22 | 23/24/19 |
| rear-A | 9/11/10 | 5/6/12 |
| rear-B | 5/6/13 | 16/20/21 |

현재 코드에서는 front-B/rear-A를 좌측으로, front-A/rear-B를 우측으로 취급한다. 하지만 현재 README와 `forklift-runtime/config/pi5-wheel-wiring.yaml`은 후방 A/B 좌우가 반대다. `reverse=True`도 현 코드 설정일 뿐 실제 전진 방향 증거가 아니다.

리프트도 현재 `mot_linear/linear_control.py`는 BCM19/26 두 입력에 PWM, EN 고정5V 방식이고 10/27 기록은22/25/13의 별도 EN 방식이다. 초음파 옛4채널(7/8,14/15,4/10,11/9)과 접촉26은 현재 바퀴/리프트 후보와 충돌한다. 어느 표도 현재 재조립 배선으로 확정하지 않는다. 기본 실물 설정에는 핀·좌우·극성을 미확정으로 두고 후보는 별도 참고파일에 보존한다. [N3][N5]

## 4. 이번 구현 계약

### 실행과 제어

1. 기본 모드는 `mock`: 하드웨어 import/장치 열기/출력 없음. 사용자용 실행 스크립트와 한국어 웹 수동 패널을 제공한다.
2. 서버는 기본 `127.0.0.1`만 수신한다. Windows는 SSH 포워딩/VS Code Ports로 접속한다. 외부 공개·자동 부팅 서비스·로그인 시 자동 시작은 만들지 않는다.
3. 실물 모드는 명시적 `--backend real --config ...`와 검증된 설정이 필요하다. 프로그램 시작 후에도 DISARMED. ARM은 무출력 준비일 뿐 움직임 명령이 아니다.
4. 순서: 제어권 획득 → ARM → 새 조작 입력. STOP/입력 만료/연속시간 제한 뒤에는 출력0과 재무장 요구. ESTOP은 래치하고 RESET → DISARMED → 새 ARM을 거친다. ARM/RESET도 현재 세대의 짧은 일회용 서버 허가가 필요하며, STOP/ESTOP 이전의 늦은 요청으로 다시 무장하거나 새 정지 래치를 해제할 수 없다. 장애물 해소·브라우저 재접속·서버 재시작으로 자동 복귀하지 않는다.
5. 웹 키보드/누르고 있는 버튼으로 조작한다. 키 놓음, 포커스/가시성 상실, 페이지 이탈, 연결 실패 시 정지. 서버가 독립적으로 입력 만료를 감시한다. 요청은 단조 증가 순번과 짧은 서버 발급 유효기간을 사용하여 늦게 도착한 명령이 재출발시키지 못하게 한다.
6. 초기 설계값: 출력20%, 상한40%, 입력 유효300ms, 최대 연속2초, 방향 전환 정지200ms. 이 값은 보수적 소프트웨어 후보이며 실제 충분한 토크·제동·안전시간을 입증하지 않는다. 설정으로 상한을 임의 해제할 수 없어야 한다.
7. 바퀴 전체/개별 채널 조작과 리프트 조작은 배타적이다. 좌우 미확정 상태에서는 차체 이동을 거부하고, 확인된 단일 채널의 방향 식별만 별도 허용한다. 리프트는 방향·상하한·유지 조건이 확인되지 않으면 실물 명령을 거부한다.

### 출력·고장 경계

- GPIO 출력 작성자는 하나다. 프로세스 잠금과 GPIO 독점 점유를 사용하고 다른 프로그램을 강제 종료하지 않는다. 다른 팀원이 사용 중이면 이유를 표시하고 실패한다.
- 실물 backend는 Pi5/RP1을 확인하고 EN을 먼저 LOW로 확보한다. 모든 채널은 검증된 핀만 사용한다. 중복핀·미확정항목·미지원 구동방식은 장치 접근 전에 거부한다.
- 무한 PWM을 사용하지 않는다. 짧은 유한 펄스의 기한을 원 명령 만료보다 늦게 만들지 않고, 이전 출력 뒤에 긴 PWM 큐가 쌓이지 않도록 한다. 정상 STOP·예외·종료에서 전체 채널 OFF를 시도하며 실패를 숨기지 않는다. API의 유한 펄스/큐 동작은 [lgpio 공식 문서](https://abyz.me.uk/lg/py_lgpio.html)로 검토한다.
- 프로세스 내부 watchdog와 유한 출력만으로 OS정지·전원손실·기계적 하중 유지까지 보장한다고 기록하지 않는다. 실제 구동 전 현장 확인 항목을 안내한다.
- 입력 범위/타입/NaN/중복 JSON 키/오래된 순번/만료된 권한/동시 명령을 검증한다. 로그 저장 실패·출력 오류는 무출력 고장 상태로 전환한다.
- 센서가 없으면 `미연결`, 배선이 없으면 `미확정`으로 표시한다. 0cm/정상/SLAM완료 같은 대체값을 생성하지 않는다. mock 출력은 화면·로그 모두 모의임을 표시한다.

## 6. 후속 목표와 완료 증거

1. 센서만 읽기: 현재 배선 확정 후 초음파·리미트·LiDAR·카메라·NFC를 각각 확인, 시각·만료·실패 원인 기록.
2. 수동 주행+관찰: Windows UI 지도/영상, 제동거리·이동/회전 보정. 엔코더 없는 wheel odometry를 실측으로 가장하지 않음.
3. 하단 한 건: ID/목적지 확인, 정렬, 정지, 집기, 운반, 분리, DB 실제 결과 기록. 실패 시 중단·중복방지·수동복구.
4. 예외·반복: 장애물/사람/센서손실/지도만료/DB실패/재시작·통신상실과 정지 확인.
5. 상단·여러 작업: 구조·하중·유지 검증 이후 별도 목표로 확장.
