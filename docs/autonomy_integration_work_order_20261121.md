이 문서는 소형 자율 물류 지게차의 **통합 관측·실물 진단·보정·강화학습**을 위한 후속 작업지시서다. 사용자의 요청에 따라 코드를 작성하기 전에 요구사항과 팀 경계를 정리한다. 기존 수동 제어 소프트웨어의 완료와 새 자율 기능의 완료를 구분한다. 센서 실시간 화면은 아래에 구현 요구사항을 정의한 상태이며, 현재 실측 영상·거리 화면이 연결되었다는 뜻은 아니다.

최종 목적은 입고 → ID 확인 → 목적지 결정 → 이동 → 포크 정렬·삽입 → 들기 → 운반 → 하단 적치·분리 → 기록을 관측 증거에 따라 수행하고, 실패 데이터에서 원인을 좁혀 검증된 코드·보정·정책을 개선하는 것이다. 상단 적치는 구조·하중·리프트 검증 후 별도 범위로 확장한다.

## 1. 이번 문서가 지키는 기준

- 초음파·LiDAR·카메라를 같은 화면과 같은 시간·좌표 기준으로 관찰한다. 원시값과 통합 결과를 모두 보존한다.
- 움직임 실패를 의도된 보호정지, 통신·시각, 제어 코드, 전기·기계, 인식·추정, 원인 미확정으로 구분한다. 증거 없이 하나로 단정하지 않는다.
- 실시간에는 감지·기록·행동 제한·정지를 수행한다. 코드·정책·기하 보정의 후보는 재생·모의·회귀 시험을 거쳐 정지 상태에서 교체한다.
- 보상 최적화와 출력 허가를 분리한다. 충돌·낙하·과주행을 반복해서 경험해야만 학습할 수 있는 구조로 만들지 않는다.
- 센서만으로 보이지 않는 차체 외곽, 초기 리프트 위치, 하중, 원인을 정확히 알 수 있다고 가정하지 않는다. 관측 불가능하면 UNKNOWN과 추가 측정 요구를 남긴다.
- 모든 현실 경우의 수를 열거했다는 완료 선언 대신, 시나리오 등록부와 미시험 조건을 계속 확장한다.
- 새 코드는 기존 팀원의 원본·서비스·인증·GPIO 소유권을 바꾸지 않는 별도 통합 영역에서 개발한다.

### 이미 확인된 구현 범위

수동 패키지는 방향·PWM 비율·정지·관찰 기록을 제공한다. 센서 취득, 위치 추정, 자율 이동, 강화학습은 아직 구현하지 않았다. Windows 74개 중 73개 통과·POSIX 전용 1개 건너뜀, 같은 실행 코드의 Pi5 Linux 74개 통과는 수동 패키지의 모의/가짜 GPIO 시험 결과다. 자율주행·센서 정확도·실물 제동의 검증 수치로 재사용하지 않는다.

공유 코드는 [수동 제어 PR #1](https://github.com/kduez5/forklift/pull/1)과 [팀원 공유 브랜치](https://github.com/leejunhee0813/forklift/tree/codex/manual-station)에 있다. 원본 main 병합 전이다.

## 3. 팀원 작업과 겹치지 않는 책임 경계

아래는 v0.5의 기존 자료 제공 분야를 기준으로 한 경계다. 새 RL 업무의 담당자·일정이 확정되었다는 뜻은 아니다. 담당 배정은 기존 공동 작업실에서 정한다.

| 기존 영역 | 원 담당 문서가 소유하는 것 | 이번 통합 작업이 받는 것·만드는 것 |
| --- | --- | --- |
| LiDAR·SLAM·인식 | 드라이버, pose/객체 생산자, Hailo 환경, 기존 알고리즘 | 원본을 읽는 어댑터, 시각·품질·좌표 검사, 겹침/사각 표시, 통합 품질 평가 |
| 모터·리프트·전원 | 배선·극성·EN, 구동 HAL, 기계/전원 실측 | 제한된 행동 요청, 응답 모델·잔차 분석, 코드/기계 원인 가설과 재현 자료 |
| 초음파·안전 코어 | 전기 조건, 센서 취득, 단일 출력, 외부 차단, 안전 상태전이 | 센서 품질 표시, 입력 계약 시험, 차단 이유 기록. 안전 규칙은 학습기가 변경하지 않음 |
| NFC·작업 기록·권한 | ID, 작업/DB 계약, 중복, RESET/ARM, 저장·재시작 의미 | episode/작업 ID 연결, 독립 성공 판정, 관측·진단·보상·버전 이력 |
| 신규 통합·학습 | 별도 지정 필요 | 대시보드, 진단기, 시나리오 등록부, 후보 학습·평가·승격·롤백 |

구현 시 새 영역은 제안 경로 `autonomy_lab/`, `integration_contracts/`, `evaluation/`로 격리한다. 이는 아직 생성하지 않은 경로다. 각자 `codex/` 작업 브랜치에서 개발하고 계약 변경은 PR로 검토한다. 원본 파일 덮어쓰기, 팀원 프로세스 강제 종료, 패키지 전체 업그레이드, 공용 서비스 자동 재시작을 하지 않는다.

실물 출력 프로세스는 공동 배치 한 곳의 단일 관리자만 소유한다. 개인 clone은 mock/replay용이다. 파일 경로마다 생기는 잠금만으로 여러 clone의 GPIO 경쟁이 방지된다고 가정하지 않는다. 센서 장치도 소유자를 한 명으로 정하고 가능하면 기존 생산자의 스트림을 구독한다. 센서 읽기도 포트 재설정·GPIO 충돌을 일으킬 수 있다.

## 5. 전체 구조와 공통 메시지

데이터 흐름은 **팀 센서 생산자 → 어댑터 → 시간·좌표·품질 검사 → 상태 추정/통합 지도 → 임무 판단·정책 후보 → 독립 제한·안전 감독기 → 단일 구동 관리자**다. UI와 기록기는 이 흐름을 관찰한다. 학습/패치 생성기는 저장된 로그를 소비하며 출력 장치를 직접 열지 않는다.

`manual_station`의 claim/arm/command를 반복 호출해 자동 운전으로 바꾸지 않는다. 현재 수동 계약의 300ms 만료·2초 burst·정지 후 재ARM은 수동 시험 목적이다. 자율 제어권 전환은 기존 안전 코어와 맞는 새 계약을 명세·시험한 뒤 연결한다. 수동 우선권 전환은 정지→기존 권한 무효화→새 권한·새 목표 순서다.

모든 메시지는 최소 `schema_version, source_id, physical_mount_id, frame_id, sequence, sample_time, receive_time, clock_domain, max_age, validity, quality, calibration_version`을 가진다. 거리 m, 각도 rad, 속도 m/s·rad/s, PWM %는 서로 다른 타입이다. 원시 단위와 변환 출처를 함께 남긴다.

시각 만료에는 단조 시계를 사용하고 로그 대조에는 UTC를 함께 기록한다. 재부팅으로 단조 시계가 초기화되면 session_id도 바꾼다. 카메라 프레임, 라이다 스캔, 초음파 에지 시각을 수신 시각 하나로 대체하지 않는다. 각 센서의 품질값은 확률로 보정했는지 단순 점수인지 명시한다.

관측 메시지와 행동 요청을 분리한다. 행동은 목표, 모드, 유효기간, 순번, 허용 구역, 사전 조건, 정책/보정 버전을 포함하며 감독기가 승인·축소·거절한 이유를 기록한다. 오래된 행동은 재전송되어도 재출발시키지 않는다. 학습 전이는 실제 적용 행동에 연결하고, 위험 요청의 거절 비용은 원 요청에 별도로 연결한다. 감독기가 위험 요청을 정지로 바꾸어 얻은 무사고 결과를 원래 위험 행동의 성공으로 학습하지 않는지 시험한다.

## 6. 한 화면의 관측·진단 요구사항

| 화면 영역 | 반드시 보여줄 것 |
| --- | --- |
| 카메라 | 원본 영상, 캡처 시각·FPS·age, 노출/흔들림/가림 상태, ID/물품/포크/지지면 후보와 신뢰도, 추론 지연 |
| LiDAR | 스캔 점/무효각, 실제 전방 화살표, 센서 원점, 차체·포크·화물 외곽, 지도/pose와 불확실성, 스캔 age |
| 초음파 | 물리 방향별 거리·FOV 부채꼴, 최소/최대 범위, timeout/무효/포화, 마지막 유효 시각, 순차 발사·간섭 상태 |
| 통합 상면도 | 중복 관측·상충 관측·unknown·가림·후방/측방 사각, 목표·경로·예상 회전 영역·정지 영역 |
| 동작·기구 상태 | 명령 방향/PWM, 관측 이동량·속도, 리프트 추정 높이/범위/UNKNOWN, 상하한, 하중/접촉 상태 |
| 진단·학습 | 정지 이유, 원인 가설과 근거, 센서/코드/정책/보정 버전, 단계별 보상과 제약 위반, 현재/후보 정책 비교 |
| 시스템·팀 상태 | 제어권 보유자/관찰자, 모드·ARM·ESTOP, CPU/온도/저장 공간, 제어·센서 주기, 입력·출력 heartbeat |

동일 시간축의 재생·일시정지·앞뒤 탐색과 사건 전후 묶음 내보내기를 제공한다. 영상과 지도에 값이 남아 있어도 stale이면 회색/만료 표시로 바꾸고 현재 값처럼 사용하지 않는다. mock/replay/live 상태는 항상 보인다. 실패한 센서는 0cm 또는 정상값으로 채우지 않는다. 연결·새로고침·보기만으로 제어권이나 ARM을 얻지 않는다.

성능 기준은 하드웨어 측정 후 결정한다. 먼저 각 스트림의 실제 주기·지연 p95/p99·최대값, 프레임 손실, 제어 지연을 기록하고 예산을 정한다. 영상 표시를 낮추더라도 안전 감시를 늦추지 않는다. 화면 끊김과 장치 센서 끊김을 구분한다.

## 7. 좌표·방향·기하 보정

1. **기준 정의:** 완성 차체에 전방 화살표·좌우·base 원점을 표시한다. 실제 지게 방향과 일치하는 전방 정의를 문서화한다. 센서 제조사 영점, 카메라 화면 방향, 모터 코드 이름을 전방 증거로 쓰지 않는다.
2. **실측 등록:** 줄자·기준 표적 등으로 센서 위치/각도, 차체 외곽, 바퀴 접지 위치, 포크 길이/폭/높이 범위, 화물 돌출을 측정한다. 측정 도구·방법·사진/표적·반복 오차를 기록한다.
3. **정지 표적 시험:** 앞/뒤/좌/우와 서로 다른 거리·높이에 기준물을 두고 센서 ID, 거리 부호, yaw, 좌표 변환을 대조한다. 센서 하나만 움직였을 때 다른 센서로 오인하지 않아야 한다.
4. **제한된 이동 시험:** 후속 실물 조건을 만족한 뒤 빈 차체의 짧은 전후 이동·좌우 회전을 외부 기준 관측과 대조한다. 미끄러짐과 보정 오차를 분리하고 여러 거리/각도에서 재현성을 확인한다.
5. **후보 추정:** 영상·라이다 정합 및 알려진 표적에서 외부 보정과 응답 모델을 추정한다. 추정이 불가능한 축, 스케일 모호성, 관측 부족을 표시한다. 바닥 한 평면만으로 모든 3D 기하가 결정되었다고 하지 않는다.
6. **갱신:** 현재값·후보값·불확실성·독립 검증 잔차를 비교한다. 좌표/방향/장착값 교체는 정지 상태에서 하고 관련 지도·모델의 유효성을 다시 검사한다.

권장 좌표 규약은 차체 x 전방·y 좌측·z 위, 카메라 optical z 전방·x 우측·y 아래다. 단위와 좌표 규약은 [ROS REP 103](https://github.com/ros-infrastructure/rep/blob/master/rep-0103.rst), map/odom의 연속성·보정 차이는 [REP 105](https://github.com/ros-infrastructure/rep/blob/master/rep-0105.rst)를 참고한다. ROS 도입을 이미 확정했다는 뜻은 아니며 동일 의미를 비ROS 계약에도 적용한다.

### 히트박스 규칙

초기 외곽은 완성 차체 실측을 감싸는 보수적인 다각형/높이 범위에서 시작한다. 보호 영역은 **차체 ∪ 포크 ∪ 화물 ∪ 회전 중 휩쓸리는 영역**에 위치·보정 불확실성과 제동 여유를 더한다. 2D LiDAR 평면이 포크 아래·상단 돌출·화물 전체를 본다고 가정하지 않는다.

센서 추정으로 더 큰 돌출·불확실성이 발견되면 보호 영역을 확대하거나 정지시킨다. 작게 추정되었다는 이유로 운행 중 자동 축소하지 않는다. 축소는 독립 실측·반복 검증 후 정지 상태에서 별도 보정 버전으로 적용한다. 작은 틈을 통과해 보며 외곽을 시험하지 않는다.

동적 footprint의 기능 근거는 [Nav2 Costmap 2D](https://docs.nav2.org/rolling/configuration_and_development/configuration_guide/core_servers/costmap_2d/)다. 이 기능이 실제 형상 추정의 정확성을 보장하는 것은 아니다.

## 8. 센서 융합과 인식 학습

- 초음파는 FOV 안의 반사 거리이며 정확한 한 점 좌표가 아니다. arc와 불확실성을 보존한다. 무응답·범위 밖·흡음·사선·센서 고장을 구분하고, 무응답을 자유 공간으로 사용하지 않는다. 근거: [ROS Range 메시지](https://github.com/ros2/common_interfaces/blob/rolling/sensor_msgs/msg/Range.msg).
- LiDAR/카메라/초음파의 공통 시야와 높이 차이를 지도에 표시한다. 평면별 점유·자유·unknown을 구분하고 포크·화물의 자기 가림을 반영한다. 한 센서의 부재가 다른 센서의 장애물 검출을 지우지 않게 한다.
- 센서 상충은 시각 오차, 변환 오차, 범위/재질, 움직이는 물체, 가림, 고장 후보로 분해한다. 가까운 장애물 증거를 다수결 평균으로 없애지 않는다.
- 같은 원시 LiDAR에서 나온 RF2O와 SLAM 등 상관된 출처를 독립 증거처럼 중복 가산하지 않는다. 카메라 탐지와 같은 영상으로 계산한 성공 신호도 독립 근거가 아니다.
- 초음파 발사 순서·간격과 crosstalk를 시험하고 기존 담당 취득 모듈의 인터페이스로 받는다.
- 추적 물체는 위치·속도·출처·확률/품질·관측 나이를 가진다. 재관측 없는 track은 만료시킨다. 배경 지도와 이동 물체를 분리한다.
- 사각으로 이동해야 한다면 그 방향의 유효 관측·정지 거리·기구 외곽 조건이 필요하다. 제자리 회전도 포크/화물이 측면을 휩쓸 수 있으므로 자동으로 안전하다고 보지 않는다.
- 인식·융합은 우선 라벨된 기록과 기준 표적으로 평가한다. RL은 이후 재관측 행동·센서 가중치 후보 등의 제한된 선택에 사용한다. 안전 감시 센서를 무시하거나 임계값을 임의 변경하는 행동 공간은 만들지 않는다.
- 융합 학습의 보상은 독립 기준과의 거리/분류 오차, 놓친 장애물, 불확실성 보정, 지연·재관측 비용으로 나눈다. 센서끼리 동의하는 정도만 보상으로 쓰지 않는다. 미관측 정답은 UNKNOWN으로 남겨 잘못된 자기 라벨의 확산을 막는다.

## 9. 엔코더 없는 이동·리프트

| 대상 | 사용할 수 있는 추정 | 보장할 수 없는 것·필수 조건 |
| --- | --- | --- |
| 차체 이동 | LiDAR/영상 상대 이동, 외부 표적, 명령 이력 기반 모델 | PWM×시간은 실제 거리 아님. 질감 부족·반복 구조·가림·슬립에서 위치 불확실성 증가 |
| 차체 회전 | 라이다/영상 회전량과 고정 표적 기준 | 바퀴 회전 명령이 차체 yaw를 보장하지 않음. 하중·바닥별 응답 시험 |
| 리프트 초기 위치 | 검증된 위치/거리 센서 또는 기준 리미트 | 재시작 전 저장 높이를 현재 높이로 인정하지 않음 |
| 리프트 이동 중 높이 | 위치 피드백이 있으면 측정, 없으면 검증된 시간 모델의 오차 구간 | 시간 추정만으로 정확한 상단 적치/끝단 회피 보장 불가 |
| 리프트 끝단·끼임 | 리미트·전류·높이 변화·시간을 함께 사용 | 전류 상승만으로 정상 끝단과 물품 끼임을 구분할 수 없음 |
| 하중 유지 | 기계 유지·제동·전원 손실 시험 결과 | 명령 OFF가 하중 고정 또는 낙하 방지를 뜻하지 않음 |

리프트는 UNKNOWN → 기준점 확인 → 제한 범위 이동 상태를 사용한다. homing은 정상 작동을 검증한 기준 센서, 이동 방향, 최대 시간·거리/스트로크 경계, 하중 조건, 독립 차단을 갖춘 경우에만 정의한다. 처음부터 끝까지 밀어 걸리는 지점을 원점으로 삼지 않는다.

리미트 고착 ON/OFF, 상하한 동시 ON, 반대 방향, 전원 복귀, 재시작, 수동으로 위치를 바꾼 상태를 시험한다. 접촉센서 하나를 양쪽 끝단·높이·하중·적치 완료의 만능 증거로 쓰지 않는다.

요구 정밀도에 비해 관측 오차가 크면 위치 센서/엔코더/추가 거리 센서 등 하드웨어 보완을 요구사항으로 남긴다. 소프트웨어로 정확히 알 수 없는 값을 성공으로 대체하지 않는다. 기구 수정과 센서 추가는 원 담당 영역에서 검토한다.

## 10. 실패 진단·시나리오 등록부

복합 시험 축은 빈차/허용 하중, 화물 크기·색·재질·무게중심, 바닥·경사, 전진/후진/회전, 전압, 조명, 센서 가림·손실·지연, CPU 부하, 통신·재시작이다. 단일 고장→위험도 높은 쌍별 조합→경계값→새 사건 순으로 확장한다. 미시험 조합과 적용 불가 조건을 명시한다.

## 11. 임무 상태와 실제 성공 판정

제안 상태는 IDLE → IDENTIFY → LOCALIZE → APPROACH → ALIGN → INSERT → LIFT → VERIFY_LOAD → TRANSPORT → ALIGN_DROP → LOWER → VERIFY_SUPPORT → WITHDRAW → VERIFY_RELEASE → COMPLETE다. 각 단계에는 관측 사전 조건, 행동 상한, 종료 증거, timeout, 가능한 복구와 복구 횟수 상한을 둔다.

주행과 리프트 동시 동작은 기존처럼 배타로 시작한다. 하중 높이·주행 속도·경사·회전 제약은 실제 기구 검증 결과에서 정한다. 자동 복구도 원 행동과 같은 안전 감독을 거치며, blind 후퇴나 반복 밀기를 기본 복구로 두지 않는다.

- 집기 성공: 포크와 물품의 상대 자세·지지 상태가 확인되고, 허용된 미소 상승 뒤 실제 동반 이동 등 독립 증거가 있어야 한다.
- 적치 순서: 물품의 지지·하중 이전을 먼저 확인하고 후퇴 경로·방향·거리 제한을 갖춘 WITHDRAW로 포크를 회수한 뒤 최종 분리를 확인한다. 완전 분리가 필요한데 포크 회수까지 막는 순환 조건을 만들지 않는다. 내림 명령 수신은 적치 성공이 아니다.
- 운송 완료: 목표 ID/구역·실제 물품 결과·DB 기록이 일치해야 한다. 증거 부족이면 FAILED 또는 UNKNOWN으로 남긴다.
- 정지 이벤트를 정상 목표 도달/단계 대기(속도0), 보호 STOP, 래치 ESTOP/FAULT로 구분한다. 보호정지·접촉 등 기존 안전 계약이 요구하는 사건에는 신선한 clear→RESET→ACK→별도 ARM→새 목표를 적용한다. 장애물 해소만으로 자동 재출발하지 않는다.
- 정상 단계 대기는 신규 자율 감독 계약에서 출력0과 관측 조건을 유지하며 다음 단계로 넘기는 사건으로 별도 정의·시험한다. 기존 수동 STOP의 재ARM 요구를 바꾸거나 수동 API의 자동 재ARM으로 대신하지 않는다. 이 구분이 팀 안전 계약과 합의·시험되기 전 자율 실물 출력을 허용하지 않는다.

## 12. 보상·벌점과 학습 문제 정의

보상은 정책이 임의로 자기 점수를 만들도록 두지 않고 **독립 관측·판정기**가 사전에 버전 고정한 식으로 자동 계산한다. 기록 단위는 episode와 task_id이며 관측, 요청 행동, 실제 허용 행동, 결과, 보상 성분, 제약 위반을 모두 저장한다.

제안 형태는 다음과 같다. 가중치와 물리 임계값은 아직 미확정이다.

```text
r_t = w_progress * (gamma * Phi(s_next) - Phi(s))
    + verified_stage_bonus
    + verified_task_success_bonus
    - w_time * elapsed_time
    - w_control * command_variation
    - w_energy * measured_or_estimated_energy_cost
    - w_uncertainty * observable_uncertainty_cost
```

단계 보상은 episode 내 검증된 전이마다 한 번만 준다. 과거 상태로 돌아갔다가 반복 접근해 점수를 모으는지 시험한다. 에너지 계측이 없으면 추정 proxy라고 표시한다. 정책의 “성공 확률”만으로 verified_success를 만들지 않는다.

| 학습 대상 | 관측·행동 후보 | 별도 평가 기준 |
| --- | --- | --- |
| 접근·이동 | pose/불확실성·가용 공간·하중 상태에서 제한된 목표 속도/방향 또는 기준 제어기의 작은 보정 | 경로/시간, 최소 여유, 정지·개입률, 기준 제어기 대비 성공 |
| 정렬·집기 | 포크/포켓 상대 자세·높이 유효 범위에서 제한된 정렬 단계 | 실제 삽입·탑재·분리 증거, 접촉·복구 횟수 |
| 재관측·융합 | 센서 품질·age·사각에서 유효한 관측 선택/재관측 행동 | 독립 라벨 오차, 놓친 장애물, 신뢰도 보정, 지연 |
| 응답 보정 | 바닥·하중·전압 조건의 관측 잔차에서 허용된 모델 파라미터 후보 | 별도 데이터에서 직진/회전 오차·정지 성능 유지 |

충돌·낙하·리미트 초과·관측 불가 방향 이동·ESTOP·소유권 위반은 **행동 차단/중단 및 제약 위반 기록**으로 처리한다. 큰 음수 보상만 주고 계속 운행하지 않는다. 정상 보호정지 자체를 나쁜 행동으로 벌주지 않고, 그 정지를 유발한 위험 후보와 환경 사건을 구분한다.

보상 해킹 시험: 영구 정지로 벌점 회피, 단계 왕복 보상 수확, 센서 비활성화로 충돌 숨기기, stale 성공 재사용, 가짜 ID/작업 완료, 시간 종료를 성공으로 처리, 낮은 불확실성 수치를 스스로 조작, 평가 데이터 학습 유출. 안전 제한을 학습으로 완화하거나 보상 가중치를 정책이 자유롭게 바꾸게 하지 않는다.

제약과 보상 분리의 연구 근거는 [Constrained Policy Optimization](https://arxiv.org/abs/1705.10528), 보상 해킹·부작용·안전 탐색 문제는 [Concrete Problems in AI Safety](https://arxiv.org/abs/1606.06565)다. 논문의 조건부 결과를 이 실물 지게차의 안전 보장으로 옮기지 않는다.

## 13. 강화학습·현장 개선의 순서

1. 기존 팀 모듈을 기록/재생 어댑터로 연결하고 정상 기준 제어기를 고정한다.
2. 수동 관측 로그와 확인된 기하·응답 범위로 시뮬레이터/재생 평가를 구성한다. 실제 기록·합성 데이터·수정 라벨을 구분한다. 기록 재생은 인식·진단·동일 관측에서의 판단 비교에 쓰며, 다른 행동을 했을 때 미래 궤적·접촉·새 관측이 어떻게 달라지는지는 증명하지 못한다. 반사실적 결과는 시뮬레이션/제한 현장 시험으로 평가하고 데이터 밖 행동은 미평가로 남긴다.
3. 관측/행동/보상/종료/시간 제한의 의미를 고정한다. episode 종료와 시간 truncation을 구분하며 데이터의 원인 불명·고장·운영자 개입을 태그한다.
4. 시뮬레이션에서 마찰·하중·전압·deadband·센서 지연/손실·장착 오차·조명 등을 실측 가능한 범위로 randomization한다. 근거: [Domain Randomization](https://arxiv.org/abs/1703.06907).
5. 알고리즘은 행동 공간·데이터량·계산 예산에 따라 선정하고 비학습 기준 제어기와 비교한다. 특정 RL 알고리즘의 도입 자체를 완료 기준으로 삼지 않는다.
6. 고정 평가 세트는 학습·튜닝에서 분리한다. 여러 seed와 조건별 결과, 실패 사례, 성능 분산·신뢰구간을 기록한다. 관측 라벨이 부족하면 먼저 데이터 수집을 목표로 한다.
7. shadow 모드에서 후보 판단과 보상을 기록하되 제어권은 갖지 않는다. 위험 후보가 감독기에 의해 거절되는지 확인한다.
8. 이후 조건을 통과한 버전만 제한 구역·빈차에서 현재 정책과 비교한다. 다음은 허용 화물의 하단 한 건, 반복 작업, 새로운 조건 순이다.
9. 실물 운전 중 정책 버전은 고정한다. 수집 데이터는 별도 학습 프로세스/장비로 전달하며 Pi5 제어와 무제한 자원 경쟁을 하지 않는다.
10. 실물 적응이 필요하면 사전 검증한 파라미터 범위와 변화율 안에서만 제한한다. 관측 잔차 악화·불확실성 초과 시 정지/현행값 복귀한다. 구조적 코드 변경·좌표 변경·보호 외곽 축소는 이 범위에 넣지 않는다.

온라인 실물 탐색은 장래 시험 단계다. 사람 없는 제한 시험 구역, 현장 중단 수단, 검증된 구동/제동/리프트 조건, 명시된 시험 시작과 종료 조건이 충족되기 전에는 수행하지 않는다. 현재 문서 작성은 실물 출력 시작이 아니다.

## 14. 자동 진단과 코드·설정·정책 변경의 적용 과정

**관측 사건 → 증거 묶음 → 원인 가설 → 최소 재현 → 후보 수정 → 독립 검증 → 정지 상태 교체 → 한정 시험 → 유지/롤백**을 사용한다.

- 확정 결함: 입력 타입·순서·단위·타임스탬프 오류 등 재현 가능한 소프트웨어 결함은 회귀 시험과 함께 수정 후보를 만든다.
- 모델/설정 문제: 응답 지연·마찰·보정 잔차는 측정 불확실성과 조건 범위를 가진 후보 파라미터로 제안한다.
- 전기·기계 문제: 전원 저하·걸림·구조·하중 유지 문제는 현장 보완 요구를 만든다. 코드 수정이 원인을 제거하지 않으면 완료로 처리하지 않는다.
- 미확정: 여러 가설이 같은 관측을 설명하면 추가 측정·안전한 판별 시험을 제안한다. 실시간 근본 원인 확정을 보장하지 않는다.

후보는 현재 코드·센서 계약·안전 코어와의 회귀 시험을 통과해야 한다. 보상 증가와 함께 안전 지표/작업 정확도가 악화하면 승격하지 않는다. 보상 정의·안전 감독·평가 세트를 한 후보에서 모두 바꿔 성능 향상을 꾸미지 않는다.

운행 중 제어 코드 hot patch, 안전 시간·리미트 해제, 자동 RESET/ARM, EN/GPIO 직접 조작, 팀 서비스 재시작은 자동 수정 범위에서 제외한다. 정지 후 장치 출력0뿐 아니라 차체 고정·화물 지지·리프트 유지와 배포 중 무동작이 확보된 정비 대기 상태에서 권한 무효화·세션 종료·후보 원자적 교체·자가 검사·새 시작 조건을 거친다. 상승된 화물을 불안정하게 유지하거나 경사면에 있는 상태를 안전한 교체 상태로 간주하지 않는다. 실패 시 이전 버전으로 되돌리고 자동 재출발하지 않는다.

각 episode에는 `code_commit, policy_version, reward_version, safety_contract_version, calibration_version, geometry_version, map_version, wiring_version, dataset_split, hardware_configuration`을 남긴다. 단일 원인 비교를 위해 한 번에 바뀐 요소를 추적한다.

## 15. 실물 시작 조건과 수치 확정

속도·PWM·정지거리·하중·리프트 시간·관측 만료를 임의의 “안전한 숫자”로 확정하지 않는다. 현재 수동 패키지의 20% 기본/40% 상한, 300ms/2초는 소프트웨어 후보이며 실물 충분 조건이 아니다.

실물 시작 전에는 다음 근거가 필요하다.

- 실제 GPIO/포트·전압·접지·극성·EN OFF·중복 장치 없음, 채널 식별과 단일 출력 관리자.
- 물리 ESTOP/독립 차단과 정전 시 리프트 하중 유지, 시험 구역·장애물·운영자 중단 수단.
- 완성 외곽·센서 장착·시각 정합·관측 범위, 위치 불확실성과 사각 방향의 이동 금지 조건.
- 빈차/허용 하중·바닥·배터리 조건별 실제 정지 지연·거리, 최대 주행·회전 속도.
- 리프트 기준점·상하한·스트로크·최대 동작시간·허용 하중·지지/분리 확인 방법.
- 통신·센서·프로세스 실패 시 출력과 기록, 재시작 후 DISARMED/UNKNOWN.
- 실측이 없는 항목은 PENDING이며 관련 행동을 차단한다. 모의 기능 개발은 계속할 수 있다.

제동 여유는 예를 들어 `d_stop = |v| * 전체 지연 + v²/(2 * 검증된 최소 감속도) + 불확실성 여유`에서 출발하되, 감속도와 지연이 유효한 조건에서만 쓴다. 회전·미끄러짐·하중 변화는 별도 실측 영역으로 반영한다. [Nav2 Collision Monitor 지침](https://docs.nav2.org/rolling/tutorials/general_tutorials/using_collision_monitor/using_collision_monitor/)은 정지/감속 설계를 참고할 수 있지만 [공식 설명](https://docs.nav2.org/rolling/configuration_and_development/configuration_guide/core_servers/collision_monitor/configuring_collision_monitor_node/)처럼 하드 실시간 안전인증을 제공하지 않는다. 물리 차단을 대체하지 않는다.

완료 상태는 문서화됨 / 구현됨 / mock·재생 검증됨 / 현장 확인됨 / 관측 불가 / 미통과를 구분한다. 현재는 G0 문서 작성 상태이며 나머지 단계의 완료를 주장하지 않는다.

## 17. 노션을 계속 확인하는 작업 절차

매 개발 시작, 후보 채택, 실물 배포 직전에 공동 작업실·변경 로그·실측표·통합 검토·관련 담당 원문·이 지시서를 다시 읽는다. page_id, last_edited_time, 본문 해시, 채택한 요구/충돌, 확인한 commit과 담당 계약 버전을 `source_manifest`에 기록한다. last_edited_time만으로 최신 결정을 자동 채택하지 않는다.

변경이 발견되면 영향받는 요구 ID·계약·시험·시뮬레이션·정책 유효 범위를 계산한다. 팀원 변경은 원본을 덮어쓰지 않고 어댑터/별도 사본에 반영한다. 제약이 충돌하면 관련 실물 기능의 승격을 보류하고 독립 개발은 계속한다.

운전 중 노션 편집을 제어 설정에 즉시 동기화하지 않는다. 작업 종료 시 실제 증거·남은 미확정·PR·변경 요약을 이 후속 문서와 공동 변경 기록에 반영한다. 홈의 10/06 기록은 정기 점검 PAUSED이며 공동 작업실의 9/19 활성 문구는 과거 기록이다. 현재 자동화 실행 상태를 확인한 것은 아니며, 이번 요청으로 상시 자동 감시나 예약 작업을 설치한 것도 아니다. 이후 구현 작업을 시작할 때마다 이 절차를 수행한다.

## 18. 후속 구현용 Codex 프롬프트

다음은 **추후 실행용**이며 이번 문서 작성에서 실행하지 않는다. 최초 목표는 G1과 계약 검증까지로 한정하고 이후 단계는 실측 근거가 갖춰질 때 별도 목표로 이어간다.

```text
/goal
노션의 “통합 관측·실물 진단·강화학습 작업지시서 v0.1”과
팀 공동 작업실·실측표·통합 검토·관련 팀원 원문을 먼저 읽어라.
현재 원문/코드의 버전·해시와 요구 A01–A10, 시나리오 F01–F37을 연결하라.
첫 완료 목표는 G1: 센서 공통 계약·mock/replay 통합 화면·기록·진단 뼈대다.

기존 manual_station, 센서 드라이버, 항법, 모터/리프트, 안전 코어,
NFC/DB 원본을 보존하고 별도 통합 패키지와 codex/ 브랜치에서 작업하라.
팀원 모듈은 어댑터로 연결하며 GPIO/포트/프로세스 소유권을 공유하지 마라.
현재 하드웨어 핀·방향·초음파 전압·치수·리프트 위치/리미트는 미확정이다.

초음파·LiDAR·카메라 원시 화면과 통합 지도, FOV/사각/가림,
시각·age·좌표·불확실성·정지 이유·버전·현재/후보 판단을 한 화면에 구현하라.
미연결·stale·무응답·UNKNOWN을 실제 정상값으로 만들지 마라.
mock/replay/live를 명확히 구분하고 import/서버/화면 열기로 출력하지 마라.

진단은 명령→허가→출력→관측 증거로 원인을 분류하고 불확실성을 남겨라.
원인 미확정은 추가 측정으로 남기고 전원/기계 문제를 PWM 증폭으로 덮지 마라.
RL 보상 계산기는 독립 관측과 단계별 실제 증거를 사용하도록 계약만 준비하라.
안전 제약·출력 허가·RESET/ARM은 보상과 분리하고 우회하지 마라.
수동 API를 자동 재ARM하는 자율 루프로 바꾸지 마라.

코드/정책/기하 후보는 재현→회귀→독립 평가→정지 상태 적용→롤백 과정을 따른다.
차체 외곽은 실측 기반 보수 영역이며 운행 중 자동 축소하지 않는다.
무엔코더 위치·높이를 확정값으로 표시하지 않는다.

이 첫 목표에서는 GPIO/모터/리프트/실제 센서 취득·무인 운행을 실행하지 마라.
자동 부팅·공개 서버·팀원 서비스 종료·계정 복사·보호 제한 완화를 하지 마라.
mock/replay 계약 시험과 UI 검증만 수행하고 실제 장치 성공을 주장하지 마라.
G2 이후는 현물·전기·단일 소유권·구동/정지/리프트 조건의 증거를 확인한 뒤
사용자의 실제 시험 시작 범위 안에서 별도 목표로 진행한다.

각 단계 시작·후보 채택·배포 직전에 노션 변경을 재확인하라.
완료 시 구현/모의/현장 검증을 나누고 PR·시험 증거·미확정 목록을 노션에 남겨라.
목표 달성은 실제 충족한 G1 소프트웨어 범위에만 표시하라.
```
